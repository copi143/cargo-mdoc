# cargo-mdoc

## 1. 项目目标与范围定义

`cargo-mdoc` 的最终目标是：

> 在**不执行 Rust 编译流程**（不进行 feature powerset、不完整编译、不进行类型检查）的前提下，通过**静态分析 Rust 源码**，构建一套**精确描述 API 可用性条件（cfg / feature / target）**的中间表示，并基于该表示生成结构化文档数据与基础可视化文档。

该项目关注的核心输出不是“某一组 feature 下能看到什么 API”，而是：

> **每一个 API 在什么条件下存在**。

### 明确的设计约束

第一阶段（MVP 及其延伸阶段）严格遵循以下约束：

* 不运行 `rustc`
* 不进行 feature 组合枚举（避免指数级复杂度）
* 不依赖完整的语义分析与类型系统
* 不尝试还原完整的宏展开与名字解析

目标是构建一个**条件感知的 API 索引系统**，而不是一个替代编译器或 rustdoc 的工具。

## 2. 问题建模与核心思想

### 2.1 传统文档生成的问题

传统文档生成（如 rustdoc）隐含的模型是：

```text
(feature set, target) -> visible items
```

该模型在 feature 数量增加时不可避免地遭遇 **powerset 爆炸**，并且难以回答以下问题：

* 一个 API 为什么在当前条件下不可见？
* 该 API 依赖哪些 feature / target？

### 2.2 `cargo-mdoc` 的建模方式

`cargo-mdoc` 采用反向建模：

```text
item -> symbolic cfg condition
```

每一个 API 节点都关联一个**符号化的条件表达式**，用于描述其存在条件。

示例（逻辑表达，而非最终格式）：

```json
{
  "path": "tokio::spawn",
  "condition": "all(unix, feature=rt)",
  "docs": "Spawn a task"
}
```

该模型具备以下性质：

* 线性规模增长
* 可延迟求值（在任意 feature / target 组合下评估）
* 可用于多种下游应用（文档、搜索、矩阵分析）

## 3. 总体架构目标

`cargo-mdoc` 的最终系统形态由以下逻辑阶段构成：

```text
cargo-mdoc
 ├── Cargo metadata 解析
 ├── Rust 源码加载
 ├── 模块图构建
 ├── cfg 表达式解析与建模
 ├── 条件传播与合并
 ├── API 项收集（IR 构建）
 ├── 条件表达式化简
 └── 多后端渲染（JSON / HTML）
```

各阶段均以**确定性、可复现的静态分析**为目标，避免引入运行期依赖。

## 4. 核心中间表示（IR）设计目标

### 4.1 条件表达式模型（CfgExpr）

项目需要一套稳定、与具体解析库解耦的条件表达式 IR，用于表示 Rust 中的 `#[cfg]` 语义。

设计目标：

* 完整覆盖 Rust `cfg` 的布尔结构
* 不绑定到第三方 AST 或内部数据结构
* 支持后续的逻辑化简与求值

逻辑构成包括：

* 常量条件（true / false）
* feature 条件
* target / flag 条件
* 逻辑组合（all / any / not）

### 4.2 API 文档节点（ItemDoc）

每一个被识别的 API 项需要被抽象为一个独立节点，包含：

* 完整路径（模块层级展开后）
* 文档文本（doc attributes）
* 存在条件（CfgExpr）
* API 类型（函数、结构体、枚举等）

该 IR 是整个系统的**事实来源（source of truth）**。

## 5. cfg 解析与合并目标

### 5.1 属性级 cfg 解析

系统需要从以下属性中提取条件信息：

* `#[cfg(...)]`
* `#[cfg_attr(...)]`

并将其统一映射为条件表达式 IR。

### 5.2 多重条件合并规则

在同一作用域内出现的多个 cfg 条件，逻辑上等价于 **AND 组合**：

```text
#[cfg(A)]
#[cfg(B)]
=> A && B
```

该规则在后续条件传播中保持一致性。

## 6. 模块系统与条件传播

### 6.1 模块解析目标

系统必须完整支持 Rust 模块系统的两种形式：

* 内联模块
* 文件模块（`mod.rs` / `foo.rs`）

目标是构建一棵**与 Rust 语义一致的模块树**，而非简单的文件遍历。

### 6.2 条件传播原则

模块与其子项之间满足以下不变式：

> **子项的存在条件 = 父作用域条件 AND 子项自身条件**

该原则确保条件表达式能够准确反映嵌套 `cfg` 的语义。

## 7. 文档与路径解析目标

### 7.1 文档提取

系统仅关注 `doc` 属性（包括 `///` 与 `#[doc = "..."]`），不尝试解析 markdown 结构或链接。

目标是为每一个 API 节点提供最基本的文本说明。

### 7.2 路径构建

通过模块遍历维护路径栈，生成符合 Rust 规范的全限定路径：

```text
a::b::c
```

路径是 API 节点的唯一逻辑标识。

## 8. 技术栈选择与实现边界

### 8.1 Rust 后端分析工具链

`cargo-mdoc` 的核心分析逻辑使用 Rust 实现，依赖的技术栈选择以**语法级静态分析能力**与**长期可维护性**为主要考量。

后端主要职责包括：

* 解析 `Cargo.toml` 与 workspace 结构
* 加载并遍历 Rust 源码文件
* 构建模块树与 API 路径
* 提取并建模 `cfg` 条件表达式
* 生成稳定的中间表示（IR）与 JSON 输出

关键依赖及其角色定位如下：

* `ra_ap_syntax` / `ra_ap_parser`

  * 提供与 rust-analyzer 一致的 Rust 语法解析能力
  * 用于构建 AST 并遍历 item、attribute 与 doc 注释

* `ra_ap_cfg`

  * 用于解析与规范化 `cfg` 相关表达式
  * 作为条件表达式 IR 的输入来源，而非最终表示

* `ra_ap_mbe` / `ra_ap_tt`

  * 为最低限度的 `macro_rules!` 识别提供语法支持
  * 不承担完整宏展开或 hygienic 语义

* `serde` / `serde_json`

  * 用于 IR 与最终文档数据的结构化序列化

* `walkdir` / `toml`

  * 支持文件系统遍历与 Cargo 元数据加载

该后端工具链的明确目标是：

> **在不进入 rustc 语义层的前提下，最大化复用 rust-analyzer 已验证的语法基础设施。**

## 9. 前端技术栈与交互式文档最终目标

### 9.1 前端系统的最终目标定义

前端系统的最终目标不是“展示生成结果”，而是：

> **为条件感知 API 模型提供一个可计算、可查询、可解释的交互式文档界面。**

该界面应当使使用者能够：

* 在不重新生成文档的前提下，动态切换 feature / target 条件
* 精确理解某一 API 在何种条件下可用或不可用
* 从 API 级别反向追溯其条件约束来源

前端被视为 API 可用性模型的一个**查询与解释层**，而非独立的信息源。

### 9.2 技术栈选择原则

前端技术栈的选择遵循以下长期原则：

* 以结构化数据驱动 UI，而非以页面结构驱动数据
* 支持复杂条件表达式的交互式求值与过滤
* 避免与后端分析逻辑产生状态耦合

基于上述原则，前端采用：

* Svelte（响应式 UI 与低运行时开销）
* Vite（确定性构建与快速开发反馈）
* TypeScript（对 IR JSON 结构的静态约束）

该技术栈的目标不是追逐框架能力，而是确保：

> **前端能够长期稳定地承载条件感知文档这一抽象模型。**

## 10. 输出形式与下游适配目标

### 8.1 JSON 作为核心输出

JSON 输出被视为**一等公民**，是所有后续能力的基础：

* Web UI
* 搜索索引
* feature / target 过滤
* API 可用性矩阵

HTML 输出仅作为验证与演示用途存在。

### 8.2 HTML 输出目标

HTML 输出追求：

* 极简结构
* 明确展示 API 条件
* 不复刻 rustdoc 的复杂 UI

## 9. 支持边界与刻意排除项

为了保证系统复杂度可控，以下能力在第一阶段被明确排除：

* proc macro 展开
* build.rs 动态 cfg
* trait / impl 解析与合并
* 名字解析与 re-export 解析
* 完整 hygienic macro 展开

这些能力被视为**后续阶段的可选增强**，而非当前目标的一部分。

## 10. 宏支持的最低目标

`macro_rules!` 的支持仅限于：

* 识别宏中显式定义的 item
* 不尝试理解复杂模式或展开逻辑

由宏生成的 API 允许被标记为“宏生成”，但仍应进入 API IR。

## 11. CLI 行为的目标定义

命令行接口的目标是：

* 提供稳定、可脚本化的入口
* 不引入隐式编译行为

支持：

* 指定 workspace / crate
* 指定 target（仅影响条件求值）
* 指定 feature 集合（用于过滤视图，而非改变 IR）

## 12. 关键设计原则总结

* 永远不枚举 feature powerset
* 永远保留符号化条件表达
* IR 优先于渲染形式
* 语法级分析优先于语义级分析

## 13. 长期演进方向（非当前目标）

在核心模型稳定后，系统可以逐步演进：

* 与 rustdoc JSON 进行信息合并
* 引入 impl / trait 级 API 建模
* 基于 rust-analyzer 增强宏与名称解析
* 构建交互式条件感知文档 UI

这些方向不影响当前阶段的架构正确性。
